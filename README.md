# 文字转油库里 · YukuriSpeak

在 Windows 上打字，把文字以**油库里语音**发到微信或QQ当前聊天——发出去的是**微信原生语音气泡**，不是一个音频文件。

语音**完全在本机离线合成**，不调用任何在线 TTS 接口，不需要 API Key，不联网。

```
你打的字 ──▶ 离线油库里合成 ──▶ WAV ──▶ VB-CABLE 虚拟声卡
                                              │
                                      （微信的“麦克风”）
                                              ▼
                                    微信录音 ──▶ 原生语音气泡
```

---

## 功能

- **打字即发**：主窗口输入文字，点「发送语音」或按 `Ctrl+Enter`
- **全局快速浮层**：在设置里自己填一个全局快捷键（如 `Ctrl+Alt+Z`），任意程序里按它就唤起无边框输入框，`Enter` 发送、`Shift+Enter` 换行、`Esc` 取消。**默认不注册任何快捷键**，避免和你机器上已有的组合冲突；不填也能用托盘菜单里的「快速发送」
- **系统托盘常驻**：关闭主窗口只是隐藏，程序继续在托盘运行
- **中文油库里**：中文 → 拼音 → 假名 + 日语音调记号 → 油库里音色（不是棒读，会还原声调）
- **日语油库里**：日文原文（含汉字）→ 音声记号列 → 油库里音色
- **界面**：主界面顶部会显示「发送给 微信/QQ 当前聊天」，底部会写明该目标的发送方式
- **发送到微信或 QQ**：两者交互方式不同——微信是「点一下开始录音、再点发送」，QQ 是「单击语音消息 → 按住说话 → 松开发送」。程序按各自的方式驱动，坐标也各自独立标定
- **中转日**：打开主界面的开关后，你打的中文会先翻译成日文，再用日语油库里音色读出（翻译走在线 API，合成仍然纯离线）
- **8 种音色**：`f1` 灵梦 / `f2` 魔理沙 / `m1` / `m2` / `dvd` / `imd1` / `jgr` / `r1`
- **语速可调**：50–300（100 为正常）
- **设置里可试听**：用当前设置合成一句示例，从本机扬声器播放
- **发送前自检**：检查目标窗口、RDP 会话、`CABLE Output` 是否可用、播放端是否可用
- **自动切换录音设备**：微信 4.x 和 QQNT 9.x 都没有「选择麦克风」了，只会录系统默认设备。程序在发送的那几秒把默认录音设备临时切到 `CABLE Output`，发完还原成你自己的设备——所以不必让系统一直挂着虚拟麦克风（见「程序会自己切换录音设备」）
- **失败即取消**：任何一步失败都会取消微信录音状态，不会留下半截录音
- **单条上限 58 秒**：微信自身限制，超长会被拦下并提示你拆分文本
- **坐标可标定**：见下方「为什么需要标定坐标」。程序会把微信窗口固定成标定时的尺寸（位置随便放），并提供一键标定工具
- **语音开头无静音**：发送路径经过专门的延迟优化，点击语音按钮到出声只有约 80 ms，不会在语音开头留下空白（见「为什么录音开头没有静音」）
- **坐标失配时主动提醒**：发送失败且判断是坐标问题时，直接弹窗问你要不要打开标定工具
- **纯 UI 自动化**：不注入微信进程、不使用私有协议、不修改微信

> ⚠️ 用自动化给个人号发语音**违反微信用户协议，存在封号风险**。本项目面向单机、低频、自用场景，请勿用于群发或批量操作。

## 兼容性

### 已在真机验证过的版本

| 客户端 | 进程名 | 实测版本 | 状态 |
| --- | --- | --- | --- |
| 微信 | `Weixin.exe` | **4.1.13** | ✅ 完整验证 |
| QQ | `QQ.exe` | **9.9.21**（QQNT） | ✅ 完整验证 |

**除这两个版本之外，其它版本都没有验证过。**

### 微信

| 版本 | 情况 |
| --- | --- |
| **4.x**（`Weixin.exe`） | ✅ 本项目针对它开发。基于 Qt 5.15（窗口类 `Qt51514QWindowIcon`） |
| **3.9.x**（`Wechat.exe`） | ⚠️ **未验证**。进程名在识别范围内，但界面布局不同，**需要自己重新标定坐标**；录制态的绿色发送按钮检测是否成立也没有验证过 |
| 网页版 / UWP 版 | ❌ 不支持，本项目只做桌面客户端 |

另外要求：主窗口标题**恰好是 `微信`**，且**只能有一个**微信主窗口。

### QQ

| 版本 | 情况 |
| --- | --- |
| **QQNT 9.x**（`QQ.exe`） | ✅ 本项目针对它开发。基于 Chromium（窗口类 `Chrome_WidgetWin_1`） |
| 旧版 QQ 8.x / EIM | ❌ 不支持。架构完全不同，窗口结构和控件都不是同一套 |
| 手机 QQ | ❌ 不支持 |

另外要求：**只能有一个可发送的窗口**。程序按窗口决定坐标，两种界面模式都能用：

| QQ 界面模式 | 程序使用的窗口 |
| --- | --- |
| 效率模式（聊天区嵌在主面板里） | 标题恰好是 `QQ` 的主面板 |
| **经典模式**（每个聊天一个独立窗口） | 独立的**聊天窗口**（标题是联系人/群名字），主面板开着或收在托盘都不影响 |

**界面模式是标定的时候一起记下来的**，程序不会靠窗口标题去猜。这一步很关键：QQ 的**设置**、**群文件**、**天气**这些也是独立的顶层窗口，光看标题分不出它们和聊天窗口的区别，猜错就会把"按住说话"的按键动作打进设置窗口里。记下模式以后，这些窗口一律被排除在外。

所以：**换界面模式后必须重新标定**（坐标本来就是相对那个窗口的右下角记录的，模式也和它绑在一起）。设置里的标定信息会显示当前生效的模式，标定结束时也会打印出来。经典模式下如果同时开着**多个聊天窗口**，程序会报错——留一个要发送的，或把目标聊天窗口切到最前面。发送前需要**你自己手动点「语音消息」**进入语音模式。

### 环境层面的限制

| 限制 | 说明 |
| --- | --- |
| **必须在主显示器上** | 截图只能抓主屏（PIL/pyautogui 的限制），目标窗口放到副屏就检测不到录音状态 |
| **窗口尺寸 ≥ 650×500** | 低于此值坐标会失效 |
| **不能用最大化窗口标定** | 最大化窗口的尺寸程序改不了，而固定尺寸是坐标长期有效的前提 |
| **显示缩放改变后要重标** | 坐标按标定时的 DPI 记录。Windows 缩放从 100% 改到 125% 之类，像素位置就会偏移 |
| **窗口尺寸不能改动** | 坐标是按标定时的窗口尺寸比例记录的，尺寸一变就全部偏移。**不过程序在每次发送前会自动把窗口调回标定时的尺寸**，所以通常不用你操心；窗口放在屏幕哪个位置都行 |
| **不能是 RDP 会话** | 远程桌面会隔离本机虚拟声卡端点，程序会直接拒绝运行并说明原因 |
| **系统** | 只支持 Windows 10/11（用到 DPAPI、WASAPI、Core Audio） |

## 环境要求

| 项目 | 要求 |
| --- | --- |
| 操作系统 | Windows 10 / 11（非 RDP 会话——远程桌面会隔离本机虚拟声卡端点） |
| 微信 | 桌面版 4.x，已登录，保持一个主窗口 |
| QQ | QQNT 9.x，已登录，保持一个可发送的窗口（效率模式下是主面板，经典模式下是要发送的那个聊天窗口；可选，只发微信可以不装） |
| 音频 | [VB-CABLE Virtual Audio Device](https://vb-audio.com/Cable/) 标准版（`VBCABLE_Driver_Pack45.zip`） |
| Python | 3.10 或更高 |
| Node.js | 18 或更高（只用于本地合成，不需要联网） |

### 安装 VB-CABLE

本项目需要的是**标准版单根 VB-CABLE**。不需要 `VB-CABLE A+B`、`VB-CABLE C+D`、`Hi-Fi Cable` 或 `VoiceMeeter`。

1. 下载 `VBCABLE_Driver_Pack45.zip` 并**完整解压**
2. 64 位 Windows 右键 `VBCABLE_Setup_x64.exe` → **以管理员身份运行**
3. 安装驱动后，若没有新增设备，则需要**重启 Windows**
4. 重启后声音设备里会出现播放端 `CABLE Input` 和录音端 `CABLE Output`

音频从程序使用的 `CABLE Input` 播放端进去，从聊天软件使用的 `CABLE Output` 麦克风端出来。**不需要**把 `CABLE Output` 设成系统默认麦克风——程序发送时会自己切，见下面的「程序会自己切换录音设备」。

### ⚠️ 微信和 QQ 用的不是同一个"默认麦克风"

Windows 每个方向有**两个**默认设备，不同程序用的不是同一个：

| 默认 | 谁用它 |
| --- | --- |
| **默认设备（多媒体）** | 原生程序 —— **微信**（Qt） |
| **默认通信设备** | Chromium / WebRTC 程序 —— **QQ**（Chromium） |

**只把 `CABLE Output` 设成"默认设备"，微信能用，但 QQ 会从别的麦克风录音，发出去的语音永远是空的**——不管多长。这个坑很隐蔽，因为两个程序看起来在用同一套设置。

这就是程序要同时覆盖**三个角色**（默认设备 / 默认通信设备 / 控制台，控制台一并切掉只是多一次调用）的原因——漏掉某个客户端真正在用的那个，症状就是一条空语音，很难查。

### 程序会自己切换录音设备

微信 4.x 和 QQNT 9.x 都已经**取消**了「选择麦克风」的设置项（老 QQ 有过，现在没有了），它们只会录系统默认设备。所以设置里有一个开关，**默认开启**：

> **发送时自动把默认录音设备切到 CABLE（发完自动换回）**

开启后，程序在发送的那几秒里把上面三个角色全部临时指向 `CABLE Output`，发完立刻还原成你原来的设备。所以平时可以把默认麦克风设成**你自己的真实麦克风**，不用一直挂着虚拟线缆。

代价要说清楚：**那几秒内，其他正在使用麦克风的程序（语音通话、OBS、会议软件）会收不到声音**。程序把这段窗口压到最短——音频先准备好、窗口先切好，然后才切设备，紧接着就是点击录音。

如果程序在发送中途崩溃，设备可能来不及还原。程序会在**下次启动时自动还原**，还原记录写在 `%USERPROFILE%\.youkuli-chaspeak\capture_swap.json`（正常发完这个文件会被删掉）。

关掉这个开关就回到手动模式：需要自己把 `CABLE Output` 设为默认设备**和**默认通信设备，程序发送前会照旧检查并拦截。

随时可以自查：

```bat
python tools\check_default_devices.py
```

它会显示三个角色当前的设备、`CABLE Output` 是否存在、以及程序能不能自动切换。

## 使用

1. 打开微信，进入要接收语音的聊天
2. 运行程序，输入文字
3. 点「发送语音」，或按 `Ctrl+Enter`

程序会自动切到微信、进入录音模式、把合成好的音频播进虚拟麦克风，再点发送。

### 建议先做的三件事

1. 点右上角齿轮进设置，用「▶ 试听」调好**语种、音色、语速**——试听是从本机扬声器播放的，不经过微信
2. 在同一个设置页填一个**全局快捷键**（不填也行）。`Ctrl+Alt+Z` 在很多机器上已被占用，程序不会硬抢：被占用时启动会明确提示你换一个
3. **标定控件坐标**（见「发送目标」一节）。每个目标只需要做一次

之后在任意程序里按你设的快捷键，就能弹出快速发送浮层，打完字回车即发。

## 发送目标：微信 / QQ

在设置 →「发送到」里选择。**每一个目标都要单独标定坐标**，因为流程和按钮位置都不一样。

| | 微信 | QQ |
| --- | --- | --- |
| 进入录音 | 程序**单击**「语音按钮」（点击式开关） | **你自己手动点「语音消息」**进入语音模式 |
| 录音 | 程序播音频，再点发送 | 程序**按住**「按住说话」→ 播音频 → **松开**发送 |
| 需要标定 | 3 个按钮 | **1 个按钮**（按住说话） |
| 取消方式 | 点录音条上的「取消 X」 | **按住时按 `Esc`**（PC 端没有上滑取消，那是手机端的手势） |
| 程序结构 | `wechat.py` | `qq.py` |

**为什么 QQ 的「语音消息」要你自己点：** 那个按钮在**私聊和群聊里位置不一样**，程序定位不可靠。而「按住说话」按钮在输入栏里，两种情况位置一致，所以只标定它一个就够。

两者在代码里实现同一套接口（`enter_voice_mode` / `finish_voice_mode` / `leave_recording_mode` …），由 `targets.py` 注册，`engine.py` 只面向接口编程，所以发送流程本身对两端是同一份代码。

### QQ 未标定时会直接拒绝发送

微信给了可用的默认偏移量，QQ 没有：**QQ 工具栏上按钮挨得很近**，猜错坐标可能点到旁边的「红包」之类的控件，而不是无害地落空。所以 `qq.py` 在没标定过之前会直接报错并告诉你怎么标定，不会拿猜的坐标去点。

### QQ

QQ 只比微信多一件事：**录音键是长按而不是点击**。

因为「语音消息」按钮在私聊和群聊里位置不同，**进入语音模式这一步交给你**；程序只做后面那一步：

```python
pyautogui.mouseDown()                 # 按住「按住说话」
# … 播放音频 …
pyautogui.press("escape")             # 取消
pyautogui.mouseUp()                   # 或直接松开 = 发送
```

**用 QQ 发送时需要你自己先点一下「语音消息」**，让输入区停在语音模式。忘了也不会出事——按下的位置落在文字输入框里，只是点了一下光标，什么都不会发生。

两个可调的时间常量（`qq.py` 顶部）：

| 常量 | 默认 | 含义 |
| --- | --- | --- |
| `PRESS_SETTLE_SEC` | 0.30 | 按下后等 QQ 真正开始录音，**然后**才播音频 |
| `RELEASE_SETTLE_SEC` | 0.25 | 音频播完后等一会儿再松开 |

**`PRESS_SETTLE_SEC` 是 QQ 最关键的一个数。** QQ（Chromium）按下按钮后要过一会儿才真正开始采集，播早了开头会被吞掉、播晚了开头会有静音。两害相权取其轻——被吞掉的音频是找不回来的，静音只是难听——所以默认值给得偏保守：

- **第一个字被吞掉** → 调大（例如 0.45）
- **开头有明显静音** → 调小（例如 0.20）

坐标没标定过会直接报错并要求标定，因为 QQ 工具栏上按钮挨得很近，**没有可靠的默认值可用**。

`_release()` 里的 `try/finally` 保证**任何异常下按键都会被松开**——否则你的鼠标左键会在系统范围内卡住。按住期间鼠标不移动，避免误触别的控件。

## 中转日：打中文，发日语语音

主界面输入框下方的**「中转日」**开关打开后：

```
你打的中文 ──▶ 在线翻译 API ──▶ 日文 ──▶ 日语油库里合成 ──▶ 语音气泡
```

「语种」设置本身不会被改动——开关只是一个**本次发送的覆盖**，关掉就恢复原来的设置。

翻译发生在**点击微信之前**，所以它的耗时只会让发送慢一点，**不会**变成语音开头的静音。

### 配置翻译服务（在线）

设置 → 「翻译方式」，两种可选：

**① 有道智云文本翻译**（[openapi.youdao.com](https://openapi.youdao.com/)）

在有道智云控制台创建应用、开通**文本翻译**服务，拿到 `appKey` 和 `appSecret` 填进去。签名方式 v3（SHA-256），由程序自动计算。

**② 大模型 API（OpenAI 兼容接口）**

任何兼容 `/chat/completions` 的服务都能用：OpenAI、DeepSeek、Moonshot、智谱、通义、one-api 之类的自建网关，甚至本机的 Ollama / LM Studio。填三项：

| 字段 | 例子 |
| --- | --- |
| 接口地址 | `https://api.deepseek.com/v1`（也可以直接填到 `/chat/completions`） |
| API Key | 留空可对接不需要鉴权的本地服务 |
| 模型名 | `deepseek-chat` |

填完点**「测试翻译」**试译一句，不用先保存。

**密钥用 Windows DPAPI 加密后存在配置文件里**，只有当前 Windows 用户能解密；配置文件里不含明文。带 ● 的字段留空表示保持已保存的值不变。

### 实现说明

- 只用了 Python 标准库（`urllib` / `hashlib` / `json`），**没有为这个功能引入任何新依赖**。
- 翻译是**惰性**的：开关关闭时不发任何网络请求、不加载任何东西，对原有路径零开销。
- 翻译失败会**中止发送**并弹窗说明，不会把中文当日文念出来。

### 标定方法

双击 `tools\校准坐标.bat`（或在设置页点「重新标定」）。默认标定设置里当前选中的目标，也可以直接指定：

```bat
tools\校准坐标.bat --target wechat
tools\校准坐标.bat --target qq
```

每一步都有一个倒计时（10~20 秒），**把鼠标停好后按回车可以立即记录**，不用等满——倒计时只是为了让你把鼠标放稳。

**微信**：把鼠标依次停在三个位置，工具会自动记录

1. 输入框工具栏的**话筒按钮**
2. 手动点一下它进入录音模式，停在**绿色发送按钮**上
3. 停在录音条左侧的**取消 X** 上

**QQ**：只需要一个位置（取消用 `Esc`，进入语音模式由你手点）

1. 打开任意一个聊天，**手动单击「语音消息」**进入语音模式
2. 把鼠标停在出现的**「按住说话」按钮**上 → 自动记录

工具会先打印它选中的窗口标题（`窗口标题：'...'`），确认那就是你要发送的聊天窗口——经典模式下是聊天窗口自己（标题是联系人/群名字），效率模式下是主面板（标题 `QQ`）。这个标题还会决定**界面模式**，标定结果里会一起打印出来（`界面模式 效率模式` / `界面模式 经典模式`），并写进下面的 `ui_mode` 字段。

标定期间有两条硬要求，工具会自己检查并在不满足时拒绝或中止：

| 要求 | 为什么 |
| --- | --- |
| 窗口必须**完整落在主显示器内**（不能挂在屏幕边缘外） | 坐标是相对客户区右下角记的，窗口一半在屏幕外时参照角就在屏外，记出来的坐标会指向虚空。而且本项目的截图功能只支持主显示器 |
| 标定过程中**不要改变窗口尺寸**（移动位置没关系） | 坐标确实依赖窗口尺寸。工具每一步都会重新读取右下角，所以移动窗口不影响结果；但尺寸一变整套坐标就失准，检测到会直接作废 |

每一步记录后都会打印参照角和偏移，方便你当场判断：

```
    参照右下角：(2143, 1077)  →  相对偏移 (-991, -40)
```

**这些偏移应当是负数**（点位于窗口内部）。出现正数就说明参照角不对，别保存，先检查上面两条。

标定完工具会问你要不要**实测一次**：按住「按住说话」，然后 `Esc` 取消并松开。实测前工具会主动把 QQ 切到前台——`Esc` 只有发给 QQ 才能取消录音。

结果保存在：

| 文件 | 内容 |
| --- | --- |
| `%USERPROFILE%\.youkuli-chaspeak\wechat_offsets.json` | 微信坐标 |
| `%USERPROFILE%\.youkuli-chaspeak\qq_offsets.json` | QQ 坐标 |

删掉微信的会恢复默认值；删掉 QQ 的会重新要求标定。

`qq_offsets.json` 里除了坐标和尺寸，还有一个 `ui_mode` 字段，记录这份坐标属于哪种界面模式：

```json
{
  "client_size": [1200, 800],
  "record": [-597, -80],
  "ui_mode": "efficiency"
}
```

取值是 `efficiency`（效率模式）或 `classic`（经典模式）。发送时程序只认这个模式的窗口，所以 QQ 的设置、群文件等窗口不会被误当成聊天窗口。**旧版本标的坐标没有这个字段**，会按 `auto` 处理（退回按标题推断的老行为）——重跑一次标定就会补上。

> 标定前请先把目标窗口调成你习惯的大小、**不要用最大化**（最大化窗口的尺寸程序改不了）。

## 为什么录音开头没有静音

微信的录音是从**点击语音按钮的那一刻**开始的。所以从点击到音频真正出声之间的任何耗时，都会原封不动地变成语音消息开头的一段静音。

实测这条路径的静音由三部分组成：

| 来源 | 修复前 | 修复后 |
| --- | --- | --- |
| 点击后程序自身的死时间 | ~720 ms | ~30 ms |
| 合成出来的 WAV 自带的开头静音 | ~195 ms（视文本而定） | ~12 ms |
| VB-CABLE 路由 + 音频启动延迟 | ~120 ms | ~65 ms |
| **合计** | **~1035 ms** | **~75–110 ms** |

三处对应三个修复：

1. **点击后不做任何耗时的事。** 旧代码点击后还有两段 `sleep`（共 650 ms）、一次截图，然后才重新枚举设备、重采样、打开音频流。现在设备解析、读盘、重采样、时长校验全部前置到点击之前（`audio.prepare_output_candidates`），点击之后只剩 `audio.play_candidates` 一个动作。
2. **固定 `sleep` 换成轮询。** 旧代码点完按钮盲等 450 ms；现在每 15 ms 检查一次录音条是否出现，一出现立刻返回开始播放。这既去掉了等待，又保证了不会在微信还没开始录音时就播放（否则会切掉第一个字）。
3. **裁掉音频开头的静音。** AquesTalk 某些音声记号（例如开头的 `っ`）会产生最长约 200 ms 的起始停顿。`audio.trim_leading_silence()` 会把它裁掉，只保留 12 ms 避免削掉起音。

另外把 `pyautogui.PAUSE` 设为 0 —— pyautogui 默认在**每次调用后**都 sleep 100 ms，而一次点击是三次调用，默认行为会凭空加上最多 300 ms。

### 音频后端：一个会伪装成「有点慢」的坑

首选播放后端是 **WASAPI**（开销约 20 ms），回退到 **DirectSound** 的开销约 450 ms，而且采样率被强制降到 44100。

问题是：**PortAudio 的 WASAPI 后端要求调用线程已初始化 COM，而 Python 的工作线程默认没有。** 发送跑在 `_send_worker` 工作线程上，所以 WASAPI 一启动就失败，静默回退到 DirectSound——**除了"感觉有点慢"之外没有任何症状**。

更坑的是它抛出的错误完全指错方向：

```
Error starting stream: Unanticipated host error [PaErrorCode -9999]:
'GetNameFromCategory: usbTerminalGUID = 9324 ' [Windows WDM-KS error -9999]
```

错误里写着 WDM-KS，让人以为是设备索引错位或采样率问题，实际是 COM 单元缺失。修复就是 `audio.ensure_com_initialized()`：在碰 PortAudio 之前先对当前线程调用一次 `CoInitializeEx(COINIT_MULTITHREADED)`。

复现条件很苛刻——**主线程调用同样的代码是成功的**，只有工作线程会失败：

| 条件 | 结果 |
| --- | --- |
| 主线程，无 capture | OK |
| 主线程，CABLE Output 被占用 | OK |
| **工作线程，CABLE Output 被占用** | **FAIL −9999** |
| 工作线程 + `CoInitializeEx(MTA)` | **OK** |

所以修改音频相关代码后，**务必跑一次**：

```bat
python tools\measure_latency.py
```

它会模拟真实条件（工作线程 + 占用 CABLE Output），确认用的还是 WASAPI。这比读日志可靠，因为回退是静默的。

### 验证方法

改完代码建议跑一遍仓库自检——它会抓出两类「没有任何报错」的坑：`.bat` 用了 LF 行尾（cmd.exe 会静默跳过后续内容，表现为启动脚本一闪就没），以及微信/QQ 两个目标模块的接口不一致（只在你切到那个目标时才会炸）。

```bat
python tools\check_repo.py
```

```bat
:: 延迟预算 + 音频后端健康检查（模拟微信占用麦克风）
python tools\measure_latency.py

:: 真实端到端开头静音：录 CABLE Output，同时播 CABLE Input
python tools\measure_leading_silence.py
```

> 修改发送路径时请注意两点：
> 1. **任何加在 `enter_voice_mode()` 之后、`play_candidates()` 之前的操作，都会被录成语音开头的静音。** 需要准备什么，就放进 `prepare_output_candidates()`。
> 2. **任何在后台线程里碰 PortAudio 的代码，前面都要有 `ensure_com_initialized()`**，否则会静默丢到慢后端上。

### 分层设计

三层互相独立，任何一层都能单独替换：

| 层 | 职责 | 可替换为 |
| --- | --- | --- |
| `synth_client` / `synth/` | 文字 → WAV | 任何别的 TTS（只要产出 WAV） |
| `audio.py` | WAV → VB-CABLE | 别的虚拟声卡（改设备名即可） |
| `wechat.py` | 驱动微信录音控件 | 别的 IM（QQ 等），或别的微信版本布局 |

`engine.VoiceEngine.send_voice()` 是唯一的上层入口，GUI 和命令行都走它，所以两条路径不会各自跑偏。

### 合成 sidecar 协议

`synth/synthesize.mjs` 支持两种模式：

```bat
:: 一次性
node synth/synthesize.mjs --text "你好世界" --lang zh --voice f1 --out hello.wav

:: 自检：把中/日/原声三条路径各跑一遍
node synth/synthesize.mjs --check
```

常驻模式（GUI 用这个，引擎只启动一次，之后每次合成 0.2–0.6 秒）：

```bat
node synth/synthesize.mjs --serve
```

stdin 每行一个 JSON 请求，stdout 每行一个 JSON 回复：

```json
{"id":1,"text":"你好世界","lang":"zh","voice":"f1","speed":100,"out":"C:\\tmp\\a.wav"}
{"id":1,"ok":true,"out":"C:\\tmp\\a.wav","durationSec":1.06,"notation":"/にい'は/おす/いじ'え","voice":"f1","speed":100}
```

`lang` 取值：

| 值 | 含义 |
| --- | --- |
| `zh` | 中文油库里（中文 → 拼音 → 假名 + 声调记号） |
| `ja` | 日语油库里（日文原文 → 音声记号列） |
| `raw` | 你直接给 AquesTalk 音声记号列，原样送进引擎 |

## 已知限制

- **界面一改就可能失效**：微信和 QQ 都不暴露可用的 UI Automation 控件，只能靠像素和坐标驱动。客户端界面改动（按钮挪位置、换颜色、换图标）都可能让对应环节失效。好在坐标由标定工具自己测，**重标一次通常就能继续用**，不需要改代码。
- **第一次使用必须标定**：微信三个点、QQ 一个点。见[标定方法](#标定方法)。
- **QQ 需要你手动进入语音模式**：因为「语音消息」按钮在私聊和群聊里位置不同，这一步交给用户。忘了也不会出错，只是发不出去。
- **版本兼容范围很窄**：详见上面的[兼容性](#兼容性)一节。
- **中文质量**：声调还原依赖上游 `yukkuri-mandarin` 的算法，多音字/生僻词可能读错。这是上游算法的能力边界，不是本项目的实现问题。
- **速率与风控**：请勿高频、批量发送。用自动化给个人号发消息本身就不在微信/QQ 的用户协议范围内。

## 故障排查

| 现象 | 处理 |
| --- | --- |
| 切到 QQ 后提示「QQ 还没有标定过坐标」 | 用 `tools\校准坐标.bat --target qq` 标定「按住说话」 |
| 「需要恰好一个 QQ 聊天窗口，当前找到 N 个」 | 按提示看当前生效的模式：经典模式下是同时开了多个聊天窗口（留一个要发送的，主面板不算，或把目标切到最前）；效率模式下是主面板没开 |
| 提示「这份坐标是旧版本标的，还没有记录界面模式」 | 按标题推断的老行为，可能误选 QQ 的设置/群文件窗口。重跑 `tools\校准坐标.bat --target qq` 补上 `ui_mode` |
| 经典模式下点了「语音消息」但程序没反应 | 坐标是在另一种界面模式（或另一个聊天窗口）下标的。重跑 `tools\校准坐标.bat --target qq`，标定时用经典模式的聊天窗口 |
| 换了 QQ 界面模式后发送没反应 | 模式和坐标绑在一起，换模式必须重新标定。设置里的标定信息能看到当前生效的模式 |
| QQ 发出去的是空语音 / 没反应 | 发送前**需要在 QQ 里手动点一下「语音消息」**进入语音模式 |
| QQ 录到的不是合成音频 | 按下后 QQ 还没开始录音就播了音频。调大 `qq.py` 里的 `PRESS_SETTLE_SEC` |
| QQ 语音被切掉了开头 | 反过来，调小 `PRESS_SETTLE_SEC` |
| 「中转日」打开后按钮变灰 | 设置 →「翻译方式」还没选好，或选了有道却没填 appKey/appSecret。界面上的提示文字会直接说明缺什么 |
| 「有道翻译返回错误码 202」 | appSecret 填错 |
| 「有道翻译返回错误码 108」 | appKey 填错 |
| 「有道翻译返回错误码 110」 | 有道智云控制台里没有开通**文本翻译**服务 |
| 「点击后微信没有进入语音录制模式」 | 坐标对不上了。程序会弹窗问你是否打开标定工具，点「是」重新标定即可 |
| 每次点击都**固定偏向某个方向一段距离** | 坐标本身错了，不是窗口位置问题（偏移是常量，所以每次都偏同样多）。重新标定，并注意标定那两条硬要求——窗口没完整在主显示器内、或标定中途改了窗口尺寸，都会造成这种偏移 |
| 双击 `启动.bat` 窗口一闪就没了 | 若程序已在运行，这是正常的：第二次启动只会把已有窗口提到最前。否则窗口会停住并提示，日志在 `%USERPROFILE%\.youkuli-chaspeak\widget.log` |
| 「无法把微信窗口调整到标定时的尺寸」 | 微信可能被最大化了。还原窗口后重新标定 |
| 「快捷键已被其他程序占用」 | 在设置里换成别的组合（如 `Ctrl+Shift+F9`），或把快捷键留空改用托盘菜单 |
| 「默认麦克风不是 CABLE Output」 | 只有关掉「发送时自动切换录音设备」时才会出现。手动把 Windows 默认输入设备设为 `CABLE Output`，或把这个开关打开 |
| **QQ 发出去的语音是空的（没声音）** | 十有八九是设备问题。先跑 `python tools\check_default_devices.py`：它能看到「自动切换」是否可用（该开的都开着就没事）。若自动切换被关掉或不可用，就把 `CABLE Output` 设为**默认设备**和**默认通信设备**（见上方「微信和 QQ 用的不是同一个默认麦克风」） |
| 发送时自己的语音通话对方听不到 | 正常现象：那几秒默认录音设备被切到虚拟线缆了。把「发送时自动切换录音设备」关掉可避免（改为手动常设默认设备） |
| 程序崩溃后麦克风在别的程序里没声音了 | 默认设备没来得及还原。重开一次程序会自动还原；也可以跑 `python tools\check_default_devices.py` 看当前指向哪里 |
| 「VB-CABLE 播放端不可用」 | VB-CABLE 未装好或装完没重启 Windows |
| 「找不到 Node.js」 | 安装 Node.js 18+，或设环境变量 `YOUKULI_NODE` 指向 `node.exe` |
| 「合成依赖未安装」 | 在 `synth/` 目录执行 `npm install` |
| 「点击后微信没有进入语音录制模式」 | 放大微信窗口到 650×500 以上；确认当前聊天支持语音 |
| 「当前前台窗口不是微信」 | 手动点开目标聊天再重试 |
| 日志 | `%USERPROFILE%\.youkuli-chaspeak\widget.log` |

列出音频设备（确认 CABLE 端点名称）：

```bat
python -c "import audio; audio.list_output_devices()"
```

本项目的做法和理由：

- **绝不把 AQUEST 的引擎或音色包提交进仓库** —— `synth/` 下只声明 npm 依赖，`node_modules/` 已在 `.gitignore` 里。这是关键：**仓库本身不含任何 AQUEST 文件**，克隆下来是干净的。
- 用户按常规做法 `npm install`，AQUEST 的文件是 **npm 从上游取**的，不是从本仓库分发的。这与整个 JS 生态处理专有依赖的方式一致，也把「再分发」这个行为从本项目身上移开了。
- 合成**纯本地**，不做成联网服务。
- 明确声明音色不属于本项目。

> ⚠️ **这是一道降低风险的屏障，不是法律保证。** AQUEST 的条款是为传统二进制分发写的，「发布一个安装后会内嵌其库的源码仓库」严格解读是否算頒布，没有明确判例，也不由我们解释。真正覆盖用户的是「非营利个人免费使用」这一条；**如果你要商业化，必须先去 AQUEST 取得授权**，别指望这层结构能代替它。
>
> 另外 `aquestalk.js` 本身是 MIT，而它的作者把音色包一并放进了自己的仓库和 npm 包——**做「再分发」这个动作的是它，不是我们**。如果 AQUEST 有异议，对象也是它。

**给 fork 和维护者的红线**（做了就会从"依赖"变成"再分发"）：

- ❌ 不要把 `node_modules/`、音色 zip 或打包好的引擎提交进仓库
- ❌ 不要在 GitHub Releases 里附带打包好的一体包（含 `node_modules`）
- ❌ 不要自己镜像/托管音色包
- ❌ 不要把它做成在线合成服务
- ✅ 让用户自己 `npm install`
